Part 5The skills

Thirty-four skills carry the craft. Each is a folder with a SKILL.md entry point and, where depth warrants, references/ files loaded on demand. This part gives each skill's purpose, the mechanisms worth knowing, and its output.

5.1 Skill anatomy

Every skill file follows the same shape, which is also the shape to follow when writing a new one:

SectionContains
Frontmattername and a description that states what it does AND when to use it (this is what triggers it)
PurposeWhy this exists and what failure it prevents
InputsWhich artifacts it reads, and what it does when they are missing
MethodThe craft: decision tables, protocols, taxonomies, numbers
ProcedureThe ordered steps
Deciding factorsJudgment calls and how to make them
Probing promptsQuestions to ask the client, and to ask yourself
Quality bar / Exit criteriaThe self-check before handing off
GuardrailsWhat this skill may never do
OutputExact file paths produced
Failure modesWhat going wrong looks like, so it is recognisable early

Keep SKILL.md under about 300 lines. Depth beyond that belongs in references/, because a skill file too long to read is a skill file that gets skimmed.

5.2 Intake and discovery PHASE 0 PHASE 1

spec-intake

Classifies whatever arrived (six classes), audits it against fourteen dimensions, fills the spec slot, opens the assumption register, and runs the substitute path when there is no spec. The one step never skipped.

References: spec-audit-checklist.md (dimension by dimension, with what each absence converts into and how to read the resulting scorecard); reconstruction-interview.md (the six passes, with the questions, in order, and the anti-patterns).

Output: 00-inputs/PRD.md, spec-intake.md, assumptions.md, audit/, and 10-discovery/derived-brief.md for classes C through F.

anchor-analysis

Forensic reading of the anchor document: three passes (intended reader, extractor, skeptic), a claim typology routing each extraction to its destination, the commitment scan with authority class and blast radius, the eight-class silence taxonomy, author-intent analysis, and the internal contradictions list.

Why it cannot be skipped: questions written without it are generic, and a generic question set is visible to the domain authority within five minutes.

Output: 10-discovery/anchor-analysis.md, including the verification agenda ordered by blast radius, which is what question-generation prioritizes from.

glossary-builder

Builds the project's ubiquitous language: definitions with includes and excludes, descriptive versus rule-bearing classification, DA verification with recorded probes, client-versus-industry pairs, and collision policing across every artifact for the project's whole life.

The three collision patterns: two names for one thing (pick one with the DA, record the alias); one name for two things (split into qualified terms); and a faction split (a contradiction with an owner, not a glossary entry).

Output: 10-discovery/glossary.md. It is also the binding label source for navigation and every field in the product.

question-generation

Engineers the call's question set: four groups (process, rules, exceptions, consequences) plus a JTBD-style history group where a switch or a past attempt is in play, per-question probing ladders, answerer routing, yield-based prioritization, and a leading-question lint pass.

References: question-bank.md: per-silence-class stems, the ladder rungs, the switch/forces questions, workaround excavation (the highest-yield set in mature operations), consequence probes, and the banned forms with their rewrites.

Output: 10-discovery/questions.md, with a ladder-free share version on top sent to attendees ahead of the call.

interview-facilitation

Runs the call, user interviews and contextual observation: consent, three-column capture, probe technique, live solution separation, requirement-unfolding logging, disagreement handling, and the closing summary.

References: facilitation-technique.md: probe mechanics (silence, echo, concretize, show-me, column walk, quantify, ladder up and down, reverse, third party), bias counters for the facilitator's own biases, the seven interviewee response patterns and the move for each, the master-apprentice observation protocol with its five giveaways, and a difficult-moment playbook.

Output: 10-discovery/transcripts/{date}.md plus the side lists that feed four other skills.

contradiction-mining

Two-stage detection (model sweep with banned verbs, then the human co-satisfiability filter and a deliberate under-detection pass), a seven-type taxonomy, ranking by dependency weight, ownership assignment, and the written-confirmation loop that closes Phase 1.

Output: 10-discovery/problem-statements.md and the STATE contradictions table.

5.3 Research, knowledge and prototyping PHASE 2A

as-is-mapping

Blueprint-grade current-state capture: trigger, steps with actor and system, the visibility layer with its crossings, data movement, waits, error handling, evidence, and provenance per row. Plus variant mapping, wait-versus-touch accounting, and the pain index.

The discipline: documentary, not aspirational. Do not tidy. A neat as-is is usually a wrong one, and every personal spreadsheet found is an entity the current system failed to model.

incumbent-research

Four extraction targets (data structures, terminology, mental models, failure patterns), the teardown protocol with task walks and severity-rated heuristic findings, state harvesting, implied ERD extraction, source-quality grading A to D, and stop conditions per question.

The discipline: extraction, not admiration. Record complaints as carefully as capabilities; differentiation lives in the complaints. Research never sets a client rule.

knowledge-base

Three-group separation with ranking, same-action indexing, the upgrade scan on authority ingestion, load-bearing marks, conflict marks, citation-mandatory query answering, and the gate-time health audit.

The rule that matters: "the KB cannot answer that" is a correct and complete answer, and it routes the question rather than burying it. Never bridge with general knowledge.

style-guide-authoring

Authors the human-readable style guide and the machine-readable skills-md/ set that prompts reference instead of adjectives. Seeded from shared-specs where current, with every divergence recorded.

The test every rule must pass: could a reviewer point at a build and say "violates rule X"? If not, rewrite until they could. Files stay under about 150 lines each, one concern per file, with precedence stated in the header, because generators obey short files and skim long ones.

prompt-authoring

The six-part prompt plus the carry checklist, iterated on paper before anyone generates, versioned with a delta log. Also drafts the provisional PRD, structured against the same fourteen audit dimensions so it can be scored like a client spec.

Constraint versus assumption: would violating it make the DA say "that is wrong" (a constraint) or "that is not how I pictured it" (an assumption)? Assumptions are cheap to show and cheap to correct; constraints must hold.

throwaway-prototype

Generates from a complete prompt, enforces the timebox, spends fidelity asymmetrically, frames the build at Gate 1 as an interview instrument, and archives it with its prompt afterwards.

Named failure modes: attachment (the timebox stretches and the throwaway quietly becomes the design) and the approval demo (the gate produces nods instead of corrections, and the phase's cheapest learning window closes unused).

dummy-content

Client-format identifiers with fictitious values, domain-plausible magnitudes, boundary dates, longest-plausible names, at least one negative and one zero per numeric surface, realistic volume, plus adversarial stress content.

Why it is a spec item, not decoration: placeholder text hides column widths, number formatting, truncation, and whether a screen still behaves when a value is negative or zero. Lorem ipsum in a rule-dense screen is the review that did not happen. Never real client data, even "just for the demo".

tentative-structure

The deliberately rough first-pass set: sitemap, to-be sketches, userflow sketches, ERD sketch. All headed TENTATIVE, timeboxed, sources-lined, uncertainty-marked, with an open-questions box per sketch. Includes the group ideation clause, so the model is not the only source of divergence.

Named failure mode: polish creep. The set gets approved instead of corrected.

5.4 Convergence PHASE 2B

requirements-reconciliation

The central artifact. Per-entry reconciliation with mandatory rationale where sources disagreed, the five quality rules, dependency links, supersession, versioning with a change log, the conflict-of-entries scan, and Type B processing from any source at any time.

Named failure modes: restatement (reads like a tidy PRD, shows no disagreement, loses the reason it exists) and rationale rot (corrections applied without why).

erd-modeling

Full entity cards: identity, attributes with sources, cardinality by counterexample, closed status lists via the exhaustion protocol with the terminal check, permissions per action including four-eyes rules, the lifecycle pass, the temporal pass, and the interface-consequences note.

Named failure modes: status leakage (values discovered in Phase 3, each one a missing screen and a Type B), interface-blind lifecycle (the delete button that legally cannot exist), temporal corruption (a price change silently rewriting a year of invoices), and central-noun collapse.

to-be-design

The target process argued against its as-is pair: replacement accounting per pain-marked row, the improvement ladder with the second-job check, automation honesty with four failure-mode answers per automatic step, human decision points with their information needs and service expectations, unhappy paths per step, two-way requirement tracing, and the projected pain-index delta.

process-breakdown

The rule layer developers build against: actor, system, input, output, rule with REQ-ID, exception with handler and resulting state, and downstream effects per step. Plus the three cross-checks (state machine in both directions, coupling pass, permission check) and the two-developer test.

Its quality metric is external: the count of build-time questions the breakdown already answered should approach the count of build-time questions.

ux-flow-optimization

Step accounting (decisions, K/R/N inputs, waits, navigations, recalls with as-is baselines), the six friction classes, the five-rung elimination ladder, the defaults doctrine, progressive disclosure rules, the error-prevention hierarchy, the recovery hierarchy (undo > confirm > warn > nothing), the friction budget sized to consequence, and wait design.

Named failure mode: speeding what should have been deleted. Rung 5 applied where rung 1 was available.

information-architecture

Structural inventory, navigation model selection with rejected alternatives, depth-versus-breadth rules, glossary-bound labelling, wayfinding, cross-cutting placement (settings, admin, reporting, notifications, search, audit, help, bulk), tree-test and card-sort validation, and the route scheme.

The rule that does most work: statuses are not places. Two candidate areas holding the same entity in different states are one area with a filter.

userflows-sitemap

Role-based flows (one per role per primary task), permission-aware branching where a denied role's experience is designed per case, exception joins received explicitly, and the entity-derived sitemap with the feature list used only as a final coverage check.

prioritization

Method selection across seven frameworks with the situations each fits, estimate provenance, the facilitated PO-plus-DA trade session, the mandatory-partition audit against authority classes, the completeness pass, role-coverage and flow-dependency sanity checks, and the signed list.

Named failure mode: must-inflation. MoSCoW without the authority audit, every stakeholder's favourite marked Must, and the method reporting a consensus that does not exist.

5.5 Production intent PHASE 3

hifi-spec

The nine blocks per feature, the state enumeration table built before any screen, the ERD consequences note consumed before designing, REQ-ID citation throughout, and self-reconciliation of status mapping against the ERD before the gate.

visual-design

The hierarchy method (name three levels, spend position then size then weight then colour, squint and five-second tests), the systematic floor, density selection as a domain decision, status encoding, data display rules, and elevation as a z-order language.

References: type-scale.md (worked modular scales with line heights, measure, weight, numerals, truncation strategies, accessibility interactions); color-system.md (role architecture, ramp construction, the contrast formula with thresholds, status encoding, chart colour, dark mode, forced colours, and a verification procedure); layout-and-space.md (the 4px scale, optical adjustment, grids and containers, alignment, composition patterns, page anatomy, concrete density tables, and a review checklist).

component-architecture

Control selection from the shape of the decision, the complete state matrix per component (universal, container, and one per ERD status), composition and slotting rules, the rule of three, naming and API conventions, and the per-component accessibility contract.

References: component-states.md (matrices for button, input, select, table, list item, modal, form, status badge, nav item, and the page-level empty/error/permission surfaces); control-selection.md (four questions that pick the control, then tables per decision shape).

interaction-design

Feedback timing thresholds, optimistic versus pending versus confirmed with the three eligibility conditions, validation timing, autosave and dirty state, the keyboard contract with focus rules, motion, selection and inline editing and drag, and concurrency handling.

References: motion-tokens.md (durations, easings, what may animate, choreography, loading motion, reduced-motion mapping, hard limits); interaction-patterns.md (per-pattern decisions a developer will otherwise make alone: buttons, forms, pickers, tables, overlays, notifications, search, dates, files, permissions, session).

responsive-design

The role-by-context table established first (device, environment, input, session length), content-derived breakpoints, the order of collapse, five dense-data strategies with selection criteria, touch and pointer rules, zoom and reflow compliance, density preference, and print/export.

The question it answers first is not "what are the breakpoints" but "who uses this, on what, where, and with what on their hands". Gloves, sunlight, shared terminals and 1366-wide laptops all change the design and none appears in a spec unless asked for.

content-design

Terminology binding to the glossary, voice set concretely, label rules, the four error kinds, the four distinct empty states, confirmation copy sized to consequence, helper text that carries a rule with its REQ-ID, and number/date/unit formatting.

References: microcopy-patterns.md (worked examples per surface: errors by kind, the four empties, confirmations by consequence tier, buttons, status transitions, loading, and translation-safe writing).

accessibility

The WCAG 2.2 AA floor as a design-time constraint: seven design-time constraints, per-artifact obligations, and a six-rung testing ladder from keyboard-only through screen reader to testing with disabled users.

References: wcag-checklist.md: every level A and AA criterion expressed as what a design artifact must contain, plus the AAA criteria worth adopting selectively and when.

Named failure mode: audit-at-the-end, when the tokens, components and flows are all settled and half the findings are unaffordable.

5.6 Quality, gates and close

design-critique

The seven lenses in order (hierarchy, consistency, state completeness, accessibility, content, flow friction, domain fidelity), the fast perceptual tests, four severity levels mapping to Type A and B, the session protocol for running it with people, and the filed report.

Lens 7, domain fidelity, is the one the rest of the design world does not have, and the reason this process exists: does anything on screen contradict a confirmed requirement, offer what the lifecycle forbids, or fail at month-end?

gate-review

Readiness pre-checks, the universal protocol, per-gate specifics, quiet-review handling, classification discipline, client-validation processing, and post-gate verification.

process-evaluation

The standing conformance engine: the traceability matrix, the four sweeps, the conformance snapshot with its headline and metrics strip, and the cadence.

Named failure modes: matrix theatre (a beautiful spreadsheet maintained by hand-invention over uncited artifacts), cadence decay, severity inflation, and evaluator capture (the evaluation run by the same agent whose artifacts it checks).

handoff-package

The full-artifact manifest with gaps listed as gaps, the what-if sweep, the live walkthrough in manifest order, the routing rule, and the question split.

md-spec-loop

The cross-project improvement loop: evidence gathering, divergence adjudication with three outcomes, the build-time question interrogation, dating and versioning, and the three loop metrics.

Why it is worth protecting: it is the only step that pays out on the next project rather than this one, which makes it the easiest to skip. A stale shared file is worse than none, because it produces confidently non-conforming output that looks reviewable and is not.
