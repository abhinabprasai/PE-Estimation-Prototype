Part 2Core mechanics

Nine mechanisms do the actual work of keeping this process honest. Everything in Parts 3 through 7 is an application of one or more of them. This is the part worth reading closely.

2.1 Provenance: tags and confidence

Any statement that describes the client's world (a problem, a rule, a process step, a status, a permission, a preference) carries a source tag and a confidence marker wherever it is written down. Both, always, in every artifact.

Source tagMeaning
[PO]The product owner said it
[DA]The domain authority said it
[TEAM:name]A team member raised it, named
[DOC:section]The anchor document, with its section reference
[USER:role]An end user, by role, from an interview or observation
[RESEARCH:source]External research, with the source named
[LLM]Model inference, not yet verified by any human
ConfidenceMeaning
(confirmed)The domain authority has confirmed it, in writing or on a recording
(asserted)A human said it once, unverified by the authority
(inferred)Derived by reasoning or by a model; no human has said it
Hard rules

A domain rule with only [LLM] provenance never enters a design artifact; it goes to open-questions.md for verification. [RESEARCH] informs design decisions but never sets a client rule: industry convention is not the client's reality. When two tagged statements conflict, do not pick a winner; record the conflict. If you catch yourself writing an untagged claim into an artifact, stop and tag it; if you cannot tag it, it does not go in.

Why the distinction between (asserted) and (confirmed) is worth the friction

A single human saying something once is evidence that it might be true. The domain authority confirming it in writing is evidence that the project can be held to it. Those are different things, and the gap between them is where most late-discovered requirement defects live. The system's answer is mechanical: behaviour-constraining claims (a rule, a status, a permission, a lifecycle property) must be (confirmed) before Gate 2. Everything still (asserted) sits in a visible open-items list with an owner, and open items block the gate. Visibility is the mechanism; nobody has to remember.

2.2 The verification ladder

Three rungs, and each artifact type is allowed only certain rungs.

RungAllowed in
[LLM] (inferred) open-questions, research notes, draft prompts. Nowhere else, ever.
(asserted) Problem statements, tentative artifacts, the provisional PRD draft.
(confirmed) Refined requirements, ERD constraints, status mapping: anything a developer will build against.

2.3 Contradictions are deliverables

Consolidation that smooths disagreement away destroys the most valuable output of discovery. When the anchor document says one thing and the domain authority says another, that gap is the finding. It is surfaced, tagged on both sides, given an owner and a due date, and pushed into STATE.md. Unowned contradictions block the Phase 1 exit.

This has a concrete consequence for how models are used. The consolidation instruction is always "list the contradictions between these sources". The verbs merge, reconcile and harmonize are banned from the instruction, because a fluent model asked to reconcile will produce a smooth, plausible, single narrative, and the disagreement it dissolved was the thing you were paying to find.

Contradictions are typed, because the type predicts who must resolve it and how urgent it is:

TypePatternResolution path
FACTDifferent values (daily vs weekly, 30 vs 45 days)Cheap; one is stale. DA rules, often same week
RULEDisagreement on what is allowed or requiredExpensive and load-bearing; blocks dependent ERD work
SCOPEDisagreement on what the project coversPO-owned; unresolved, it poisons prioritization
PROCESSDifferent sequences for the same workOften BOTH true: map the variants, do not pick
VOCABULARYSame word, different meanings by factionGlossary collision; route with an owner
AUTHORITYDisagreement on who decides or overridesPolitically hot; handle in a small setting, not a gate
DOC-VS-REALITYThe document commits to something the room deniesThe classic finding; usually "document is old", but confirm

2.4 Gates

A gate produces exactly three things: a held-or-not-held fact, a classified correction list, and a filed report. Nothing else counts as a gate.

GateRequired attendeesWhat it validates
Gate 1Domain authority + product owner The Phase 2A set reviewed together: prototype, as-is flows, tentative ERD, sitemap, to-be sketches. A screen can be accepted while its data model is rejected, and only a joint review catches that.
Gate 2DA + PO + at least one developer All artifacts, model first and screens last: refined requirements, ERD, breakdown, to-be pairs, flow optimization deltas, IA, userflows, sitemap. Developer acceptance of the ERD is an exit criterion.
Gate 3Internal team Line by line: each in-list feature's spec against its REQ-IDs, plus an independent re-run of the status-mapping-versus-ERD reconciliation. Passing unlocks scheduling client validation, not shipping.

Reading a gate's outcome

The quiet gate

Heavy correction at Gate 1 is success: the instrument worked. Little correction is a warning, not a pass. Either the artifact set was too safe to test anything, or the reviewer is being polite. Before a quiet gate may pass, the reviewer is probed ("complete the job on this build in front of me and narrate where it lies", "run month-end on this flow", "what does this let you do that reality forbids?"), and the report records that the probes were run.

Gate integrity rules

  • Attendance before agenda. A missing required attendee means NOT HELD, recorded as such, rescheduled. No authority overrides this.
  • Readiness pre-checks. The pre-gate critique has run with zero open blockers (or they are declared), the conformance snapshot is current, the assumption register is prepared to be read aloud. A gate entered on unknown state reviews artifacts that may already disagree with each other.
  • Disclosure before review. Open assumptions and unresolved contradictions are read aloud before the review starts. Acceptance is only informed acceptance if they were stated first.
  • Written exit. A verbal yes is recorded as (asserted) and the gate stays PASSED-PENDING-WRITTEN until confirmation arrives.
  • Post-gate verification within the week. Every routed correction is checked to have actually landed. Corrections that evaporate teach everyone that gates are theatre.

2.5 Corrections: Type A, Type B, and the rework machinery

Every correction, from any source (a gate, a design critique, client validation, a refuted assumption, a conformance finding) is classified at the moment it arrives, in the room where possible.

TypeChangesHandling
Type A
surface		 A screen, a flow drawing, wording, layout The owning agent patches in place; a note goes in STATE.md; work continues.
Type B
structural		 A rule, an entity, a status, a permission, or a requirement Routes to requirements-reconciler first, before any artifact is touched. The requirement entry is updated with a rationale, the version is bumped, dependency links are walked to mark every dependent stale, owning agents re-derive, and a rework-log row is written with the Phase 1 topic it traces to.
When unsure, it is Type B

The cost asymmetry decides. A Type A misclassified as Type B costs one unnecessary trip through the reconciler. A Type B misclassified as Type A means the requirement document and the shipped screen now disagree, permanently, and nobody knows.

There is a diagnostic built on top of this. Three or more Type B corrections tracing to the same Phase 1 topic means discovery converged too early on that topic. The system escalates with a recommendation to re-open discovery on that topic specifically, not the whole phase. 

# any correction, from anywhere
/rework "the DA says posted invoices can be amended within the same period"

→ classified Type B (touches a lifecycle rule)
→ routed to requirements-reconciler: entry updated, rationale written, version bumped
→ dependency links walked: erd.md, process-breakdown.md, 3 hi-fi specs marked STALE
→ staleness sweep run; rework-log row written
→ regeneration order reported, with the owning agent for each

2.6 Continuous conformance

Gates verify conformance at checkpoints, with humans in the room, at high cost. Between gates, the conformance engine verifies it continuously and cheaply, so gates spend their expensive minutes on domain judgment instead of on discovering that two files disagree.

The instrument is a requirements traceability matrix: every REQ-ID mapped to every artifact that implements, constrains or renders it. It is an index of citations that already exist in the artifacts, not a new bureaucracy; if a link has to be hand-invented to fill a cell, the finding is the uncited artifact.

ColumnContent
REQ-IDFrom refined-requirements.md, the single source of IDs
To-be flowWhich flow step(s) implement it, or NONE
BreakdownWhich rule row(s) enforce it, or NONE
ERDWhich entity or constraint carries it, or N/A
Hi-fiWhich feature spec(s) render it, or NOT-YET / DESCOPED
Verification methodinspection / demonstration / analysis / DA confirmation
FlagsORPHAN, GHOST, STALE, CONFLICT

Two flags carry the weight:

  • ORPHAN: a requirement nothing implements. Either it awaits its phase (fine, marked NOT-YET), it was descoped (and must appear on the descope list; if it does not, someone dropped it silently), or it was forgotten.
  • GHOST: artifact behaviour citing no requirement. Either a missing requirement to route to the reconciler, or invention to remove. Ghosts are how scope creeps in quietly and how untraceable behaviour reaches production.

The four sweeps

SweepWhat it checks
TraceabilityRebuilds the matrix from current citations; diffs against the previous one. New orphans, new ghosts, links that vanished.
StalenessWalks the dependency order. Did anything an artifact depends on change after its last edit? Mechanical, not judgmental: a stale artifact may still be correct, but nobody knows until its owner re-derives or re-affirms it.
ProvenanceUntagged claims, (asserted) sitting where (confirmed) is required, [LLM] content outside its quarantine zones, assumption-register integrity and overdue decisions.
DriftDirect document-versus-artifact comparison per layer: supersessions explicit, orphan checks both ways, ERD-versus-breakdown state machine in both directions, status mapping versus ERD, copy versus glossary.

Cadence

TriggerScope
End of each phaseFull snapshot
Before each gateFull snapshot; it is a gate readiness pre-check
After every Type B landsStaleness sweep plus affected matrix rows
Weekly during Phases 2B and 3Traceability plus staleness
On demand: /verifyCaller's choice; default full
Two disciplines that protect the mechanism

The evaluator reports and routes but never fixes: an evaluator that edits the artifacts it checks has no independence left. And severity honesty: BLOCKING is reserved for what genuinely blocks a gate, because inflating severity burns the mechanism's credibility. A snapshot older than its cadence is itself a finding.

2.7 Working without a spec

The most common real starting condition. Projects arrive with a slide deck, a two-page gap note, a Jira export, a login to an existing system, or a person saying "we will send it next week". The system makes that normal instead of blocking.

The spec slot

00-inputs/PRD.md exists in every project from the moment /new-project runs. It is one of exactly two things and never a third: the client's spec filed verbatim and read-only, or the completed placeholder record declaring the intake class and which substitute path is running. It is never absent, and never left as an unedited template. An unedited placeholder past Phase 0 is a process defect: it means nobody decided how this project would learn what it is building.

Six intake classes

ClassWhat arrivedSubstitute path
AA full specNone. Audit it, then anchor-analysis normally
BA partial specAudit marks thin areas; question generation weights them
CA gap documentAs-is reconstruction; gaps are problems, never requirements
DDeck, notes, Jira exportConsolidate into a derived brief, then get it signed
EAn existing productProduct audit as the anchor; the build shows what it DOES, never what it should
FNothingReconstruction interview producing a signed discovery brief

Four or more ABSENT scores on the fourteen-dimension audit reclassifies a project to class D regardless of how professional the document looks. A bad spec is more dangerous than no spec, because it is trusted.

The reconstruction interview

You cannot ask "what do you want built"; people answer with solutions shaped by whatever software they last used. You ask people to narrate their world, and derive the spec from the narration. Six timeboxed passes: goal (what outcome, measured how), actors (who touches it, how often, who overrides whom), artifacts (what records move through it, seen as real documents where possible), rules (what must always be true, and which are legal rather than preference), exceptions (when it breaks, who fixes it, at what cost), consequences (if this were wrong for a month, what damage, discovered by whom, when).

The output is a derived brief, structured like a spec so the same fourteen-dimension audit can score it. Signed, it becomes the anchor document. Unsigned, it caps everything downstream at (asserted), and every gate is told so in its first sentence.

The five-rung ladder

Any agent hitting a missing answer follows this, stops at the first rung that produces something honest, and marks which rung it used:

RungSourceRule
1Knowledge baseAnswered with a citation, or it says it cannot answer
2Client evidenceExisting build, exports, real documents. [DOC:source] (asserted)
3Domain authorityQueue it; escalate DA-ONLY if it blocks today
4ResearchInforms a design decision; never sets a client rule
5Assumption registerWith blast radius, cheapest test, named owner, decision date
Rung 5 is legitimate. Silence is not.

What is never allowed is skipping silently to rung 5, or producing an artifact whose reader cannot tell which parts rest on rung 1 and which on rung 5. Every artifact built on assumptions carries an ASSUMPTIONS box near its top listing the register IDs. Assumptions constraining behaviour may not pass Gate 2. A refuted assumption is a Type B correction by default.

2.8 The five adaptation variables

Read from PROJECT_CONFIG.md. They change routing; they are never guessed. If unset, the orchestrator asks and records the answers before Phase 1 work starts.

VariableValuesRouting effect
anchor_documentsupplied / none / existing-product none: a signed discovery brief must be produced first. existing-product: as-is work becomes an audit of the build; Phase 1 weights toward audit.
domain_authoritysme / end-users / both end-users or both: adds user interviews to Phase 1 and usability testing to Phase 3. sme only on a user-facing product logs risk R-SME-SUB.
rule_densityhigh / low low: ERD modelling and process breakdown become optional, and the time reallocates to UI exploration. high: both are mandatory and developer-reviewed at Gate 2.
engagement_typefixed-bid / t-and-m / augmentation fixed-bid: the prioritized list locks at Gate 2 and later changes are scope changes requiring escalation. augmentation: client documents may replace artifacts, recorded as substitutions.
designer_engagementdemo / in-team / ready-to-code / modernize demo: the prototype IS the deliverable, so throwaway framing and the archive rule are disabled and the quality bar rises. ready-to-code: the full shared-specs set is mandatory at handoff.

Two more the design layer needs, asked at project start because nobody volunteers them: accessibility obligation (sector, procurement standard, or contractual commitment above the AA floor) and device and environment per role (what people use, where, and with what on their hands). Unknown on either becomes an assumption register entry with a large blast radius; unasked, the second defaults silently to desktop, which is the most commonly late-discovered constraint in this process.

minimum_set: true reduces the mandatory artifact set for small or fast projects to: attributed problem statements, knowledge base, as-is flows, refined requirements, to-be flows, prioritized feature list, and hi-fi for prioritized features. Everything else becomes optional, but its skill still applies when invoked.

2.9 The design floor

These are constraints, not preferences. They override any conflicting instruction in a style guide, a client brand guideline, or a stakeholder's stated preference. Where a conflict is real, it is escalated, never resolved by lowering the floor.

Non-negotiable
  • WCAG 2.2 level AA on everything designed. Higher where a client's sector or procurement standard requires it; establish which at project start.
  • Meaning is never carried by a single channel. Not colour alone, not position alone, not motion alone. The greyscale test settles it.
  • Every task is completable by keyboard alone, with focus always visible and never removed without an equally visible replacement.
  • Interactive targets are never below 24 x 24 CSS px, and 44 x 44 on touch-primary surfaces, regardless of density mode.
  • Nothing flashes more than three times per second, and prefers-reduced-motion is honoured.
  • Every component is specified in every state it can reach, including every ERD status value it can display. A component specified only in its default state is not specified.
  • Status values come from the ERD's closed lists. A status appearing in a design that the ERD does not contain is a Type B correction, never a design choice.
  • No affordance the lifecycle forbids. A delete control on a reversed-not-deleted entity does not exist anywhere in the interface.
  • Every style guide rule is violation-checkable. If a reviewer could not point at a build and cite it, it is an aspiration and does not ship.
  • Real copy in every state before Gate 3. Placeholders are incomplete specs.
  • An accessibility claim states its method. An automated scan is never reported as an accessibility assessment.
