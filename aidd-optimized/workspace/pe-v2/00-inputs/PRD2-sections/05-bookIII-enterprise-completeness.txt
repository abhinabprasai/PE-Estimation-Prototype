Standard Specification Ordering Partition key = business object key (material_id, wo_id, so_id…) guaranteeing per-object ordering; consumers must not assume cross-object order 
Delivery and idempotency At-least-once delivery; every consumer keeps a processed-event store keyed on event_id (or a natural idempotency key named in the contract) — duplicate 
deliveries are no-ops by construction Retry and dead-letter Consumer retry with exponential backoff (1 s → 5 min cap) for 24 h, then dead-letter queue; DLQ items alert the owning 
team and are replayable from the integration console (§4) after cause resolution; DLQ replay preserves original event_id so idempotency still holds Replay Topics retain 30 days; 
full-history rebuild for read models via snapshot + replay procedure documented per consumer Schema evolution Additive changes only within a version; consumers tolerate unknown 
fields; breaking change = new event_type version, dual-published during migration window 2.3	Transaction	and	Consistency	Model • Atomic business transactions: the 
boundaries named in Part A field 9 (GRN, PGI, confirmation, IC pairing, disposition outcomes) execute as single database transactions covering stock, tracking, journal and outbox 
rows together. No business event is ever half-posted. • Transactional outbox: events and cross-module commands are written in the same transaction as the state change and published 
by a relay with at-least-once semantics. Direct dual-writes (DB + broker in separate steps) are prohibited. • Concurrency: optimistic locking (version column) on documents; 
pessimistic row locks only inside posting transactions (reservation firm-up, stock decrement, number-series allocation). Stock rows use atomic conditional decrements — 
negative-stock races are structurally impossible where policy forbids negatives. • Compensating actions: where a saga spans modules (RMA disposition outcomes, IC pairing rollback 
on partial config error), each step has a named compensator specified in the interface contract; sagas surface in the console with step-level state. • Clock and sequence: all 
timestamps UTC server-side; document numbers from gap-free series where finance requires (invoices) and gap-tolerant elsewhere (performance), per series configuration.
